# 관측 기반 UX 개선 설계 · 구현

운영 중인 화면을 직접 걸어보고, 분석 데이터를 붙여, **검증 가능한 개선안과 프로토타입**을 만든다.

이 skill의 전제: **상상으로 쓴 개선안은 회의에서 무너진다.** 모든 주장은 출처가 있어야 하고, 출처의 강도가 표시되어야 한다.

   ↓
[설계]  ★ 본 skill               관측 + 근거 등급 → 개선안 · 구현 규격 · 프로토타입
   ↓
[문서]  requirement-to-prototype  Baseline(C/O/D) 체계 → 기획 산출물 6종 · 배포

본 skill은 **그 문서에 들어갈 내용이 어떻게 참이 되는가**를 담당한다.

## 1. 관측 우선 (Observation First)

### 1-1. 직접 걸어본다

개선 대상 화면은 **반드시 실제로 조작**한다. 캡처만 보고 쓰지 않는다.
경로 전체를 처음부터 끝까지 통과하며 각 단계의 URL·상태 변화를 기록한다.

### 1-2. 자동화 조작 ≠ 사람 조작 — 반드시 검증한다

브라우저 자동화의 클릭이 사람의 조작과 **다른 결과**를 낳는 경우가 있다.

> 실사례: `href="javascript:;"` 요소를 ref로 클릭했더니 페이지가 리로드되며 URL 파라미터가 사라졌고,
> 그 결과 "첫 진입"이 아니라 "재진입" 상태가 렌더링됐다. 이를 첫 진입 동작으로 기록해 **핵심 페인포인트를 잘못 서술**했다.

방어 절차
- 클릭 전후 **URL을 항상 비교**한다. 파라미터가 사라졌으면 상태가 초기화된 것이다
- 핵심 동작(선택·확정·분기)은 **사용자에게 수동 재현을 요청**해 교차 확인한다
- 사용자가 "실제로는 이렇게 동작한다"고 정정하면 **즉시 원본 관측을 폐기**하고, 그 항목에 의존하던 서술을 전부 추적해 함께 고친다 (페인포인트, 다이어그램, 캡처 라벨/alt, 시연 스크립트까지)

### 1-3. 진입 경로가 여러 개면 각각 확인

같은 화면이라도 진입 경로에 따라 초기 상태가 다를 수 있다.
경로별로 걸어보고 **"본 화면은 동일, 진입부만 상이"**인지 **"화면 자체가 다른지"**를 확정한다.
차이가 진입부에 한정된다면 그 사실 자체를 Baseline 항목으로 남긴다.

## 2. 근거 등급 태그 — 이 skill의 핵심

Baseline 항목·페인포인트·수치 **전부**에 아래 중 하나를 붙인다.

| 태그 | 의미 | 함께 적을 것 |
|---|---|---|
| `[관측]` | 실제 화면에서 직접 확인 | 재현 경로 |
| `[데이터]` | 분석 도구 수치 | 기간 · 표본 수 · 도구명 |
| `[추론]` | 위 둘에서 유도 | 유도 논리 한 줄 |
| `[합의]` | 이해관계자 결정 | 결정자 · 결정 시점 |

**운영 규칙**
- `[추론]`이 Critical 등급 문제의 **유일한 근거**이면 → 사람에게 수동 검증을 요청한 뒤 `[관측]`으로 승격하거나, 등급을 낮춘다
- 확정/미확정(C/O) 구분과 **별개 축**이다. 확정된 항목도 근거는 `[추론]`일 수 있고, 그게 가장 위험한 조합이다
- 회의·보고 자료에는 `[추론]` 항목만 뽑은 목록을 따로 준비한다. 반박이 들어올 지점이 그곳이다

### 2-1. 측정 공백 처리

대상 페이지의 세션·이벤트가 **0건으로 잡히는 구간**이 흔하다. 이때
- 없는 데이터를 추정치로 채우지 않는다
- 인접 단계 지표를 **대리 지표(proxy)** 로 쓰되, 본문과 회의 자료 **양쪽에** 대리 지표임을 명시한다
- 공백 자체를 Baseline 항목으로 남긴다 — 나중에 "왜 이 페이지 수치는 없냐"는 질문이 반드시 나온다

## 3. 검증 공정 — 자기채점 금지

### 3-1. 스크립트 검증의 상습 오탐

산출물을 정규식·문자열 카운트로 검증할 때 다음이 반복해서 오탐을 낸다.

| 오탐 유형 | 예 |
|---|---|
| 접두 매칭 | `card` 검색이 `card-top`도 셈 / `r-m` 이 `r-meta`·`r-main`을 셈 |
| 셀렉터 중복 | `body` 규칙이 `html, body` 때문에 2건으로 집계 |
| 구조 오인 | `<tr><td>` 카운트가 `tfoot`까지 포함 |

**카운트가 어긋나면 "테스트가 틀렸다"고 결론내기 전에 원문 해당 위치를 직접 열어 눈으로 확인한다.**
검증 스크립트도 내가 쓴 것이므로, 스크립트와 산출물이 같은 오해를 공유할 수 있다.

### 3-2. 필수 게이트: 외부 적대적 리뷰

산출물이 완성되면 **별도 세션 또는 다른 AI**에 넘겨 `"이 산출물을 반박해봐"`로 리뷰받는다.

> 실사례로 이 게이트에서 나온 지적: 44px 터치타깃이 일부 컨트롤에만 적용됨 /
> 접근성 준수 서술이 실제 구현 범위보다 과장됨. 둘 다 내부 검증에서는 통과했던 항목이다.

지적이 나오면 방어하지 말고 **먼저 재현**한다. 재현되면 수정하고, 서술도 함께 정정한다.

### 3-3. 사람에게 남겨야 하는 검증

아래는 코드·마크업 검증으로 대체할 수 없다. **완료로 처리하지 말고 잔여 항목으로 명시한다.**
- 실기기에서의 트랜지션·스크롤 체감
- 스크린리더의 실제 음성 출력
- 키보드 포커스 링의 실제 렌더 결과
- 손으로 조작했을 때의 화면 동작 (1-2 참조)

### 3-4. 과장 금지

구현한 것보다 넓게 쓰지 않는다.

| 쓰지 말 것 | 대신 |
|---|---|
| "WCAG 충족" | "WCAG 1.4.1(색상 단독 의존) 해소. 보조기술 전달은 별도 항목이 담당" |
| "접근성 확보" | 충족한 성공기준 번호를 나열 |
| "전 항목 적용" | 적용 범위를 셀 수 있게 서술하고, 실제로 세어 본다 |

## 4. 프론트 구현 규격

### 4-1. 선택 상태 표현

- **색상 단독 금지** (WCAG 1.4.1). 최소 3중 단서: 보더 **두께 변화** + 채움 + 라디오/체크 UI 병행
- 카드 전체를 선택 영역으로 쓰더라도 **명시적 선택 컨트롤(라디오)** 을 함께 둔다 — "눌러도 되는지" 인지 비용을 없앤다
- 시각 단서와 보조기술 전달은 **별개 항목**이다. 시각만 해결하고 접근성을 다 했다고 쓰지 않는다

### 4-2. 키보드 · 보조기술

```html
<div role="radiogroup" aria-label="요금제 목록">
  <div role="radio" aria-checked="true"  tabindex="0">…</div>
  <div role="radio" aria-checked="false" tabindex="-1">…</div>
</div>
```
- **roving tabindex**: 선택된 항목만 `tabindex="0"`, 나머지는 `-1`. 방향키로 이동
- 토글 버튼은 `aria-pressed`, 상태 변경 알림은 `role="status"` 또는 `aria-live="polite"`

### 4-3. focus-visible 이중선 함정 ★

내부 요소에 `outline-offset`을 주면 **컨테이너 패딩 안쪽**에 링이 그려져, 선택 상태 보더와 겹쳐 이중선으로 보인다.
포커스 표시를 **컨테이너 바깥 헤일로**로 옮기고, `:has()` 미지원 환경은 기존 아웃라인으로 폴백한다.

```css
.item-main:focus-visible{ outline:2px solid var(--main); outline-offset:3px }  /* 폴백 */
@supports selector(:has(*)){
  .item-main:focus-visible{ outline:none }
  .card:has(.item-main:focus-visible){ box-shadow:0 0 0 3px rgba(91,75,225,.30) }
  .card.sel:has(.item-main:focus-visible){ box-shadow:0 0 0 3px rgba(91,75,225,.30), 0 6px 20px rgba(91,75,225,.15) }
}
```
CSS 레벨 검증만으로는 부족하다 — **키보드 방향키로 실제 이동시켜 눈으로 확인**한다 (3-3).

### 4-4. 부분 DOM 갱신 (통짜 교체 금지)

`innerHTML` 전체 재작성은 **스크롤 위치와 포커스를 잃는다.** 목록형 화면에서는 치명적이다.

```js
function pick(key, code){
  var st = S[key], prev = st.selected;
  if(prev === code) return;          // 동일 선택 시 무동작
  st.selected = code;
  paintCardSel(key, prev, false);    // 바뀐 노드만
  paintCardSel(key, code, true);
  setRoving(key, code);              // tabindex 이동
  paintSticky(key);                  // 종속 UI 갱신
}
```
원칙: **상태를 바꾸는 함수는 자기가 바꾼 것에 종속된 UI만 골라 다시 그린다.**

### 4-5. 터치 타깃 44px — 전수 확인

"주요 버튼 44px"로 끝내면 반드시 누락이 생긴다. 화면 내 **상시 노출 컨트롤을 목록으로 뽑아 전부 센다.**
자주 누락되는 것: 탭, 필터 칩, 셀렉트, 시트/모달 닫기 버튼, 아이콘 전용 버튼.

### 4-6. 파생 상태 붕괴 방지

목록에서 항목을 제거하면 그 항목에 의존하는 UI가 깨진다.

> 실사례: 비교 대상 2건 중 1건을 빼자 비교 시트가 열린 채 남아 `Cannot read properties of null` 로 크래시.

3중 방어를 모두 넣는다.
1. **상태 정리** — `if(st.compare.length < 2) st.sheet = false;`
2. **렌더 조건** — `st.sheet && st.compare.length === 2` 일 때만 그린다
3. **함수 가드** — `if(!a || !b) return '';`

### 4-7. 점진 렌더

목록이 길면 스크롤에 따라 나눠 그린다. 초기 렌더 비용을 낮추되, 개수 표시는 **전체 기준**으로 유지한다.

## 5. 단일 HTML 산출물

리포트와 프로토타입을 한 파일에 합칠 때.

- **네임스페이스 분리** — 리포트 크롬 클래스에 접두사(`r-`)를 붙이고, 프로토타입 CSS는 **한 글자도 건드리지 않는다.** `.view`/`.r-view`, `.tabs`/`.r-tabs` 처럼 쌍으로 확인
- **캐스케이드 순서** — `body` 같은 전역 셀렉터는 뒤에 오는 쪽이 이긴다. 병합 후 반드시 확인
- **증거 이미지는 base64 임베딩** — AS-IS 캡처를 넣어도 단일 파일 속성이 유지된다. 넣은 뒤 파일 크기를 확인하고, 각 이미지에 캡션과 `alt`를 단다 (캡션은 관측 사실과 일치해야 한다 — 1-2 정정 시 함께 고친다)
- **금지** — 외부 CDN, `localStorage`/`sessionStorage`. 상태는 메모리에서만
- JS 문법 검증
```bash
node -e "const s=require('fs').readFileSync('FILE','utf8');
const i=s.lastIndexOf('<script>')+8,j=s.lastIndexOf('</script>');
try{new Function(s.slice(i,j));console.log('JS OK')}catch(e){console.log('ERR',e.message)}"
```

## 6. 배포와 확인

- 커밋 후 **커밋 수가 실제로 증가했는지** 저장소 화면에서 확인한다. 업로드만 되고 커밋이 안 되는 경우가 있다
- 좌표 클릭 대신 **요소 참조(find → ref)** 를 쓴다. 창 크기가 바뀌면 좌표가 어긋나고, GitHub은 단일키 단축키가 있어 잘못된 포커스에 타이핑하면 다른 페이지로 튄다
- 갱신 확인은 `?v=n` 으로 캐시를 우회한다
- **Public 배포 시 실제 서비스 URL 구조와 분석 수치가 외부에 노출된다.** 배포 전 고지하고, 사내 한정 필요 여부를 확인한다

## 7. 마무리 시 반드시 남길 것

산출물을 넘길 때 아래를 **먼저** 밝힌다. 나중에 발견되면 신뢰를 잃는다.

| 항목 | 내용 |
|---|---|
| 샘플 데이터 범위 | 어디까지가 실제 관측이고 어디부터 샘플인지 |
| 지표 비교 가능성 | 플로우가 바뀌면 기존 지표와 직접 비교 불가 — 신규 기준선을 제시 |
| 검증 잔여 | 3-3의 사람 검증 항목 |
| `[추론]` 목록 | 근거가 약한 지점 (2절) |

**프로토타입의 완성도가 설득력을 과대공급한다.** 동작하는 화면은 "거의 다 됐다"는 인상을 준다.
착수 전 단계임을 명시하지 않으면 개발 견적이 과소평가된다.

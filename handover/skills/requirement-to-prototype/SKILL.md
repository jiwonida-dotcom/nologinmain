# 요구사항 → 기획 산출물 · 프로토타입 생성

요구사항을 받아 **일관된 6단계 산출물**을 만든다. 각 단계는 앞 단계를 상위 문서로 참조하며,
모든 문서는 **공통 기준(Baseline)** 이라는 단일 진실 원천을 공유한다.

> **연계 skill** — 개선 대상이 *운영 중인 실제 화면*이고 관측·분석에서 출발한다면
> `observed-ux-improvement`를 함께 사용한다. 그 skill이 **내용이 참이 되는 절차**(근거 등급, 검증 공정,
> 프론트 구현 규격)를 담당하고, 본 skill이 **산출물 체계**를 담당한다.

---

## 0. 시작 전 확인

입력 유형을 먼저 판별한다.

| 입력 유형 | 시작 절차 |
|---|---|
| **문서형** — 요구사항 시트·정의서·구두 정리 | 원문을 먼저 확보한다. Sheet/Docs URL이면 커넥터로 파싱, 이미지·PDF면 읽어 텍스트로 정리. **원문을 보기 전에 문서를 쓰지 않는다** |
| **관측형** — 운영 중인 화면 개선 | 실제 화면을 끝까지 걸어보고 URL·상태 변화를 기록한 뒤 시작한다. 절차는 `observed-ux-improvement` 1절 |

원문 파싱(또는 관측) 후 반드시 아래를 분리해 파악한다.

| 구분 | 판별 기준 |
|---|---|
| 확정 사항 | 요구사항에 값이 명시된 것 / 화면에서 직접 확인된 것 |
| 미확정 사항 | "협의 필요", "확인 필요", 값이 비어 있는 것 |
| 암묵 가정 | 문서에 없지만 구현하려면 반드시 정해야 하는 것 → **반드시 Open Issue로 올린다** |

암묵 가정을 찾아내는 것이 이 skill의 핵심 가치다. 요구사항을 그대로 옮겨 쓰기만 하면 안 된다.

## 1. 산출물 구성 (6종)

| # | 산출물 | 형식 | 목적 |
|---|---|---|---|
| 1 | 시스템 정의·설계 | `.md` | 목적·타겟·제약, 아키텍처, 데이터 플로우, 데이터 모델 |
| 2 | 상세 기능 정의서 | `.md` | 화면/URL, 검증 시퀀스, 노출 데이터, 예외 매트릭스, 백오피스 기능 |
| 3 | 화면 와이어프레임 | `.md` | ASCII 목업 + 컴포넌트 명세 |
| 4 | 기획 아티팩트 | `.html` | 위 3종을 탭으로 통합한 열람용 단일 HTML |
| 5 | 동작 프로토타입 | `.html` | 실제 클릭 가능한 단일 HTML |
| 6 | 배포 세트 | 폴더 | 랜딩 + 위 2개 HTML + README |

**산출물 원본(`.md`)도 저장소에 함께 올린다.** HTML만 배포하면 변경 이력이 남지 않아
"왜 그렇게 결정했는지"를 추적할 수 없다.

## 2. 공통 기준 (Baseline) — 가장 중요

3개 `.md` 문서 **상단에 동일하게** 삽입하고, 아티팩트의 이슈 트래킹 탭에도 같은 내용을 넣는다.
ID를 붙여 문서 간 참조가 가능하게 한다.

```markdown
## 공통 기준 (Baseline)

> 아래 표는 3개 문서와 기획 아티팩트에 동일하게 적용되는 단일 기준이다.
> 변경이 발생하면 이 절을 먼저 갱신하고 각 문서 본문에 반영한다.

### 확정 사항 (N건)
| # | 항목 | 근거 | 확정 내용 |
|---|---|---|---|
| C-01 | ... | [관측] | ... |

### 미확정 사항 (N건)
| # | 항목 | Owner | 배경 |
|---|---|---|---|
| O-01 | ... | 요청자 | 확정 전까지 무엇이 막히는지 |

### 표준 문구 · 명칭
| 구분 | 확정 값 |
|---|---|
| 화면 헤드라인 | "..." |
| CTA 버튼명 | ... |
| 예외 Alert 문구 | "..." *(미확정 시 표기)* |

### 개발 협의 항목
| # | 항목 |
|---|---|
| D-01 | ... |
```

**운영 규칙**
- 확정 = `C-nn`, 미확정 = `O-nn`, 개발 협의 = `D-nn`
- **근거 열은 비워두지 않는다** — `[관측] [데이터] [추론] [합의]` 중 하나.
  확정 여부(C/O)와 근거 강도는 **별개 축**이다. `C-nn` + `[추론]` 조합이 가장 위험하니 별도로 뽑아 검증한다.
  상세 규칙은 `observed-ux-improvement` 2절
- 각 문서의 개별 이슈 목록은 만들지 말고 "공통 기준 참조"로 일원화한다
- 사용자가 항목을 확정하면 → Baseline 갱신 → 본문 반영 → 문서 버전 올림 → 카운터(확정 N건/미확정 N건) 일치 확인
- **관측 사실이 정정되면** 그 항목에 의존하는 서술을 전부 추적해 함께 고친다
  (페인포인트, 다이어그램, 캡처 라벨·alt, 시연 스크립트, Before/After 블록)

## 3. 문서별 필수 구성

### 3-1. 시스템 정의·설계

```
| 문서 버전 | vN.N (변경 요약) |
| 작성일 | YYYY-MM-DD |
| 근거 문서 | 원문 출처 |
```

- **시스템 정의**: 목적(번호 매긴 2~3개), 타겟(3주체), 기대 효과, 핵심 제약사항
- **아키텍처 개요**: ASCII 박스 다이어그램 (레이어 표기 — EXTERNAL / FRONT 신규 / FRONT 기존 / API / BACK)
- **데이터 플로우**: mermaid `sequenceDiagram` — 정상 분기 + 예외 분기를 `alt/else`로
- **화면 구성 표**: 화면 / 신규·기존 / 역할
- **데이터 모델**: 컬럼·타입·설명 (PK, FK, 제약 명시)
- **도메인 경계**: 서브도메인·시스템이 갈리는 지점을 명시한다. 상태 승계 방식(파라미터/세션)이
  달라지는 원인이며, 개발 협의 항목의 근거가 된다

### 3-2. 상세 기능 정의서

- **화면 및 URL 정의**: 구분 / 화면 / 신규·기존 / URL / Method
- **검증 시퀀스**: `STEP n | 처리 | 검증 조건(판정식) | 실패 시` 표.
  조건은 산문이 아니라 **판정식**으로 쓴다 (`use_yn = 'Y'`, `start_dt ≤ now ≤ end_dt`)
- **노출 데이터**: 항목 / 소스 / 노출 형태 / 화면 조작 가능 여부
- **예외 처리 매트릭스** (아래 3-4 참조)
- **백오피스**: 리스트(검색·그리드·페이징) / 등록·수정(입력 항목별 검증·오류 처리) / 저장 처리 / Audit
  - **신규 관리 항목이 정말 필요한지 먼저 따진다.** 기존 데이터·기존 배치로 충족되면
    "백오피스 신규 요건 없음"이 가장 강력한 추진 근거가 된다

### 3-3. 화면 와이어프레임

ASCII 목업은 **반드시 스크립트로 생성**한다. 한글은 2칸을 차지하므로 손으로 맞추면 어긋난다.

```python
import unicodedata
W = 92
def dw(s):
    return sum(2 if unicodedata.east_asian_width(c) in 'WF' else 1 for c in s)
def L(s=''):
    return '│ ' + s + ' ' * max(0, W - dw(s)) + ' │'
TOP='┌'+'─'*(W+2)+'┐'; BOT='└'+'─'*(W+2)+'┘'; SEP='├'+'─'*(W+2)+'┤'
```

주의사항
- `▼ ※ « ●` 등 **ambiguous width 문자는 박스 안에서 피한다** (환경별 폭이 달라 정렬이 깨짐).
  `v`, `*`, `<<`, `(*)` 로 대체
- 내부 표는 폭을 계산해서 만든다: `w = max(dw(x) for x in lines) + 1`
- 각 화면 뒤에 **컴포넌트 명세 표**(영역 / UI 컴포넌트 / 동작 정의)를 붙인다
- 리스트형 화면을 빠뜨리지 않는다 — 등록/수정만 그리는 실수가 잦다
- 생성 후 **전 블록의 정렬을 스크립트로 재검증**한다 (오류 0건 확인)

### 3-4. 예외 처리 매트릭스 (공통 패턴)

| ID | 예외 케이스 | 발생 조건 | 상태 처리 | Alert 메시지 | 확인 시 이동 | 비고 |
|---|---|---|---|---|---|---|
| EX-01 | ... | 판정식 | ... | 문구 또는 "없음" | 목적지 | 미확정 시 ⚠ 표기 |

**반드시 함께 정의할 것**
- 우선순위 (`EX-01 > EX-02/03 > EX-04`) 및 선순위 발생 시 후순위 검증 미수행 여부
- Alert 형태 (단일 버튼 / 닫기 제공 여부 / 딤 클릭 동작)
- 이동 시 파라미터·정보 유지 여부
- **케이스별 상태 처리가 다른 이유** — 이 근거를 별도 문단으로 남긴다

## 4. 기획 아티팩트 (HTML)

`mcp__cowork__create_artifact` 로 생성. 탭 구조:

```
개요 | 시스템 정의·설계 | 기능 정의 | 화면 설계 | 이슈 트래킹
```

**작성 규칙**
- **외부 CDN 금지.** 아티팩트 샌드박스는 chart.js/grid.js/mermaid 외 전부 차단된다. CSS·JS 전부 인라인
- `:root { color-scheme: light }` + 자체 CSS 변수 정의. 호스트 전용 변수에 의존하지 말 것
- 개요 탭에 **SVG 아키텍처 다이어그램**을 넣는다 (박스 + 화살표, 레이어 라벨, 신규 대상만 강조 테두리)
- 화면 설계 탭은 ASCII가 아니라 **실제 UI에 가까운 HTML 목업**으로 그린다
- 이슈 트래킹 탭 = Baseline의 C/O/D + 표준 문구

**프로토타입과 한 파일로 합칠 때**
- 리포트 크롬 클래스에 **접두사(`r-`)를 붙여 네임스페이스를 분리**하고, 프로토타입 CSS는 손대지 않는다
- `body` 같은 전역 셀렉터는 병합 후 캐스케이드 순서를 확인한다
- AS-IS 캡처 등 증거 이미지는 **base64 임베딩**으로 단일 파일 속성을 유지한다. 캡션과 `alt`를 반드시 단다

**독자 수준에 맞춘 용어**
- IT 실무자 대상이 기본: 검증 시퀀스, 폴백, read-only 렌더, 어트리뷰션, 채번, Audit
- 비개발자 대상이면 풀어쓰되, 설계 판단의 **근거**는 반드시 남긴다

## 5. 동작 프로토타입 (HTML)

단일 HTML + 인라인 CSS + Vanilla JS. `localStorage`/`sessionStorage` 금지 — 상태는 메모리에서만.

**백오피스 탭**
- 목록 화면(검색 필터 → 실제 필터링, 그리드, 상태 배지, 페이징) ↔ 등록/수정 화면 전환
- 입력 검증이 실제로 동작: 유효 코드 통과 / 잘못된 코드 차단 + 인라인 오류
- 코드 자동 채번, 목록 반영, 행 클릭 시 수정 화면 진입(값 복원 포함)

**프론트 시뮬레이터 탭**
- 시나리오 버튼: 정상 진입 + 예외 전건 (선택 상태를 JS로 다시 그릴 것 — 정적 강조는 첫 버튼만 켜진 채 남는다)
- 좌측에 **검증 로그**: STEP별 PASS/FAIL/SKIP 표시
- Alert → 확인 → "OOO 페이지로 이동합니다" 결과 출력
- 정상 진입은 다음 화면까지 이어지게 하고, 승계된 값을 화면에 노출
- **백오피스로 건너가는 링크**를 둔다 (목록 열기 / 해당 데이터 수정 화면 열기)

**사용자 조작이 있는 화면이면** 접근성·부분 DOM 갱신·터치 타깃·파생 상태 붕괴 방지 규격을
`observed-ux-improvement` 4절에 따라 적용한다. 통짜 `innerHTML` 교체는 스크롤과 포커스를 잃는다.

**검증**
```bash
node -e "const s=require('fs').readFileSync('FILE','utf8');
const i=s.lastIndexOf('<script>')+8,j=s.lastIndexOf('</script>');
try{new Function(s.slice(i,j));console.log('JS OK')}catch(e){console.log('ERR',e.message)}"
```

## 6. 배포 (GitHub Pages)

```
deploy/
├── index.html        랜딩 (두 산출물 카드 링크)
├── plan.html         기획 아티팩트
├── prototype.html    프로토타입
├── docs/             산출물 .md 원본
└── README.md
```

**주의**
- **평면 구조로 만든다.** 웹 업로드는 폴더 구조를 유지하지 못한다
- 빈 저장소는 브랜치가 없어 업로드가 막힌다 → `.nojekyll` 같은 파일을 먼저 만들어 `main` 생성
- 업로드 후 Settings → Pages → `main / (root)` → Save
- 모든 페이지 상단에 **공통 네비게이션**(홈 / 기획서 / 프로토타입, 현재 위치 강조)
- 갱신 후 확인 시 `?v=2` 등 쿼리로 캐시를 우회한다. Pages는 HTML을 최대 10분 캐시한다
- **Public 저장소면 실제 서비스 URL·정책 구조·분석 수치가 외부에 노출된다.** 배포 전 반드시 고지한다

브라우저 자동화로 대신 배포할 때
- **좌표 클릭 대신 요소 참조(find → ref)** 를 쓴다. 창 크기가 바뀌면 좌표가 어긋나고,
  GitHub은 단일키 단축키가 있어 잘못된 포커스에 타이핑하면 다른 페이지로 튄다
- 커밋 후 저장소 화면에서 **커밋 수가 실제로 증가했는지 확인**한다. 업로드만 되고 커밋이 안 되는 경우가 있다

## 7. 진행 원칙

**변경 요청이 오면**
1. Baseline 먼저 갱신
2. 3개 문서 본문 반영
3. 아티팩트·프로토타입·배포본 동기화
4. 버전 번호와 카운터 일치 확인

일부만 고치면 문서 간 불일치가 쌓인다. 한 번에 전부 반영한다.

**항목을 삭제할 때 참조 고아를 확인한다**
개발 협의 항목·예외 케이스를 지우면 본문에 남은 `D-nn`·`EX-nn` 코드가 갈 곳을 잃는다.
삭제 후 해당 코드를 전문 검색해 **자기완결적 서술로 치환**한다. 수치가 담긴 표를 지울 때도
그 수치가 다른 곳에 남아 있는지 먼저 확인한다.

**검증 스크립트를 맹신하지 않는다**
정규식·문자열 카운트는 접두 매칭(`card`가 `card-top`을 셈), 셀렉터 중복(`html, body`가 2건),
구조 오인(`tfoot` 포함)으로 상습 오탐을 낸다. 카운트가 어긋나면 **"테스트가 틀렸다"고 결론내기 전에
원문 해당 위치를 직접 열어 확인**한다.

**완성 후 외부 리뷰를 거친다**
별도 세션 또는 다른 AI에 넘겨 "이 산출물을 반박해봐"로 검토받는다. 내부 검증을 통과한 항목에서
실제 결함이 나온다. 지적이 오면 방어하지 말고 먼저 재현한다.

**설계 판단을 추가했을 때**
요구사항에 없던 내용을 넣었다면 반드시 그렇게 표시하고 근거를 남긴다.
사용자가 "그건 요구사항이 아닌데"라고 하면 즉시 범위를 분리하거나 제거한다.

**요구사항과 충돌할 때**
사용자 지시가 우선이다. 다만 그 결정으로 생기는 부작용(예: 세션 소실 시 복구 경로 없음,
멀티탭 덮어쓰기)은 문서에 남기고 협의 항목으로 올린다.

**문서에 남길 것 vs 남기지 말 것**
- 남길 것: 판정식, 우선순위, 예외 분기 근거, 미확정 항목의 Owner와 배경, 근거 등급
- 남기지 말 것: 확정되지 않은 URL 실제 경로, 추측한 수치, 근거 없는 기본값

**세션이 끊길 것을 전제한다**
대화 기억이 아니라 문서가 진실의 원천이다. 새 세션 시작 시 Baseline 문서를 먼저 읽고 착수한다.
